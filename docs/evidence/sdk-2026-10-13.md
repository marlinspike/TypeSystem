# The typed SDK against the baseline, 2026-10-13

Slice 4 of the [roadmap](../roadmap.md),
[ADR-0055](../adr/0055-typed-sdk-generated-from-the-registry.md). Compared
with [`baseline-2026-10-13.md`](baseline-2026-10-13.md). Nothing here is a
user study: the comparison is what the compiler now checks, and what the
same question takes to write.

## The baseline question, rewritten

*The F-16s that need attention, with their components' part numbers, as
the current user.*

```ts
const af = createClient<AirforceModel>(runtimeTransport(runtime, identity));

for await (const aircraft of af
  .from("airforce.Aircraft")
  .where({ model: "F-16C" })
  .where((a) => a.needsAttention.eq(true))
  .select("tailNumber", "needsAttention")
  .include("components", (c) => c.select("partNumber"))
  .all()) {
  const parts = aircraft.components.map((c) => c.partNumber); // (string | undefined)[], no casts
}
```

The baseline version needed a client-side filter (computed properties
could not be filtered in a query, which also broke paging) and an
unchecked cast for every value.

## The baseline friction, item by item

| Baseline friction | Now | Evidence |
|---|---|---|
| Type, property, relationship and Action names are strings checked only at run time | Checked by the compiler against the generated model | `packages/sdk/test/types.test.ts`: twelve `@ts-expect-error` cases that fail `npm run typecheck` if they ever compile |
| Every value is `unknown`; generated interfaces aren't connected to results | Rows typed through selections and nested includes; computed values typed by a declared, runtime-enforced `schema` | `types.test.ts`; `codegen.test.ts` (`ComputedValueError`) |
| Computed properties can't be filtered; client-side filtering breaks paging | Fixed in the runtime by ADR-0054; the SDK compiles to it | `client.test.ts`, `computed-filter-pagination.test.ts` |
| Invoking an Action means knowing its name and input shape by hand; no "what would happen" | Typed `action(name).preview(input)` / `.invoke(input)`; `actions(type, id)` lists what this caller may do | `client.test.ts`, both transports |
| Agent discovery reads every full schema | Not addressed by this slice (slice 5) | — |
| No workflow model | Not addressed by this slice (slice 6) | — |

## Equivalence, not a second implementation

For six representative queries and three callers (maintainer, viewer,
anonymous), the SDK returns exactly what `runtime.query` returns for the
`SemanticQuery` it builds, in process and over MCP; anonymous is refused
identically on every path. Six runtime mutations and one type mutation are
each caught (ADR-0055 lists them).

## Performance

`npm run benchmark`, in-memory adapter, 500 runs each, four runs today:

| Operation | Baseline p50 ms | Today p50 ms (range of runs) |
|---|---|---|
| `getObject` | 0.078 | 0.102 to 0.230 |
| `query` + filter (200 rows) | 16.157 | 16.17 to 16.66 |

An A/B run with the new computed-value check removed measured `getObject`
p50 0.149 and 0.102 against 0.230 and 0.105 with it: within run-to-run
noise. `getObject` is slower than the baseline across slices 1 to 4; the
cause is not yet attributed and is listed in the roadmap's remaining gaps.
The SDK's own overhead (building a query, converting rows) was not measured
separately.
