## Developer experience, as found

What a developer writes today to answer one question: *the F-16s that need
attention, with their components' part numbers, as the current user.*

```ts
const page = await runtime.query(
  {
    type: "airforce.Aircraft",          // a string; a typo is a runtime NotFoundError
    filter: { property: "model", operator: "eq", value: "F-16C" },
    include: [{ relationship: "components", select: ["partNumber"] }],
    select: ["tailNumber", "needsAttention"]
  },
  identity
);
const needing = page.items.filter((a) => a.values.needsAttention === true); // computed: cannot be filtered in the query
for (const a of needing) {
  const parts = (a.values.components as ResolvedObject[]).map((c) => c.values.partNumber as string);
  //                         ^ every value is `unknown`; every cast is unchecked
}
```

Observed friction, each checked against the code:

- Type names, property names, relationship names and Action names are
  plain strings. Nothing is checked until the runtime throws.
- Every value is `unknown`. `typesys generate-types` emits interfaces, but
  nothing connects them to `query` results, includes or projections.
- A top-level filter or sort on a computed property is refused
  (`rejectComputedFilterProperties`), so the developer filters a page
  client-side, which also breaks paging (a page can come back empty with
  more matches behind it).
- Invoking an Action means knowing its name and input shape from its
  JSON Schema by hand; there is no way to ask "what would happen" first.
- An agent discovering the model reads every Type's full schema
  (`typesys_list_types`): 4 Types in the airforce domain already return
  several kilobytes, and there is no ranking, no compact form, and no way
  to check a composed query before running it.
- There is no workflow model: approvals, retries, idempotency and
  compensation are the application's own code.
