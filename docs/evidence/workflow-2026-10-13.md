# Governed workflows against the baseline, 2026-10-13

Slice 6 of the [roadmap](../roadmap.md),
[ADR-0057](../adr/0057-governed-workflows.md). Compared with
[`baseline-2026-10-13.md`](baseline-2026-10-13.md), which found no workflow
model: approvals, retries, idempotency and compensation were each
application's own code.

## What a workflow author no longer writes

The demo, `airforce.GroundForRepair`
([`ground-for-repair.ts`](../../packages/domain-airforce/src/workflows/ground-for-repair.ts)),
is eight declared steps: two reads, two compute steps, an AI triage, a
lead's approval, and two Actions, one with a compensation. Its source is
136 lines, 13 of them comments. Each row below is behavior the
author gets by declaring it, with the test that shows it:

| Behavior | Declared by | Shown in |
|---|---|---|
| Reads and Actions authorized, classified and audited as the person who started the run | nothing | `workflow.test.ts`: "reads as the initiator..." |
| Who may start the run | `startPolicy` | "refuses a caller the start policy does not admit" |
| An approver other than the initiator, admitted by policy, refusals audited | `kind: "approval"`, `policy` | "refuses the initiator approving their own run..." |
| The model's answer checked against a schema and recorded as the model's | `outputSchema` | "an answer outside the output schema fails the step" |
| No side effect from an AI answer no person reviewed | `needs` (checked at registration) | "refuses an Action with side effects fed by an AI step no approval reviewed" |
| Retries for retryable errors only, with backoff | `retry` | "retries a retryable failure with backoff, and only that" |
| Undo of completed Actions when a later step fails | `compensate` | "closes the work order it opened when a later step fails" |
| Recovery after a restart without repeating reads, model calls or Actions | nothing | "resumes after a restart from the journal alone" |
| No repeat of a non-idempotent Action whose outcome was lost | nothing (from the model's `idempotency`) | "never repeats a non-idempotent Action whose outcome was lost" |
| A changed definition refused for runs it cannot reproduce | nothing | "the engine will not resume a run under a definition that diverges" |
| A dry run against live data, with faults and crashes | `simulate(...)` | `simulate.test.ts` |

Lines of code are a proxy for effort, not a measure of it; no comparison
with a hand-written equivalent was timed.

## What it costs

300 runs of the demo after a warm-up, in process, in-memory sources with no
simulated latency, Node 22, each a full run (start, then a lead's
approval). "Direct" makes the same reads and Actions with
`SemanticRuntime` calls and no engine. Two runs:

| | p50 | p95 |
|---|---|---|
| Direct | 7.92 ms, 7.91 ms | 9.20 ms, 9.99 ms |
| Engine | 8.81 ms, 8.83 ms | 11.20 ms, 10.60 ms |

About 0.9 ms more per run at p50, for 19 journal events (each written through
`structuredClone`), two policy decisions, three audit rows, a replay check
before each advance, and the compute steps and model call the direct path
leaves out. Both grow over the 300 runs because `needsAttention` scans every
work order and each run adds one. The journal here is in memory; a durable
one adds a write per append.

## A core defect found on the way

One full test run failed: slice 3's computed-filter test timed out at 5 s.
Alone it takes about 0.3 s; after the rest of the suite it took 3.3 s
without this slice's tests and 4.9 s with them. A CPU profile of an ordered
run put about 10% of all time in Node's `AsyncLocalStorage` propagation:
every `SemanticRuntime` created its own `AsyncLocalStorage` for its request
context, and on Node 22 each live one is propagated on every promise the
process creates and is never released, so every runtime ever constructed
made every later `await` slower. A process that builds runtimes (per
tenant, per test, per configuration reload) degrades the same way. The
runtime now shares one per process, with each request context naming the
runtime it belongs to, so instances still never share a budget or an
audited operation (`request-concurrency-budget.test.ts`, both properties
mutation-checked). In the full suite the test now takes 236 to 319 ms. The
`npm run benchmark` numbers, which build one runtime, are unchanged within
their noise.

## Is the governance right?

Eleven mutations of the engine and the definition check, each caught by at
least one test (listed in the ADR). The first run of the mutation check
found two gaps in the tests, not the engine: nothing asserted that a
non-retryable error is tried once even under a retry policy, and nothing
exercised the replay check on `resume` (only on `approve`). Both are now
asserted.
