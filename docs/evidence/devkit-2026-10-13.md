# Discovery, validation and contract diff against the baseline, 2026-10-13

Slice 5 of the [roadmap](../roadmap.md),
[ADR-0056](../adr/0056-model-description-discovery-validation-and-contract-diff.md).
Compared with [`baseline-2026-10-13.md`](baseline-2026-10-13.md), which
found that an agent discovering the model reads every Type's full schema,
with no ranking and no way to check a composed query first.

## What an agent reads to find its way

Measured on the demo registries (core's Types included), bytes of JSON or
text:

| Registry | Types / Actions | `typesys_list_types` | Compact catalog | `typesys_discover`, top 2 |
|---|---|---|---|---|
| airforce | 10 / 2 | 8,492 | 2,663 (31%) | 744 (9%), for "close a work order" |
| hospital | 9 / 0 | 8,221 | 1,806 (22%) | 743 (9%), for "a patient's upcoming appointments" |

Bytes are a proxy for tokens, not a token count. The registries are
small; the listing grows with every Type, while a discovery answer is
bounded by `limit`.

## Does discovery find the right thing?

Six tasks written before the ranking was tuned, over both domains
together (19 Types, 2 Actions). The intended Type or Action ranked first
for all six:

| Task | First match |
|---|---|
| which aircraft need attention | `airforce.Aircraft` |
| close a work order | `UpdateWorkOrderStatus` |
| open a work order for a maintenance event | `CreateMaintenanceWorkOrder` |
| a patient's upcoming appointments | `hospital.Appointment` |
| part condition of installed components | `airforce.Component` |
| where is the jet deployed | `airforce.Aircraft` |

And one it cannot answer: "which doctor specializes in cardiology" matches
nothing, because the hospital model says `Provider` and `specialty`, never
"doctor". Two tuning changes were made after the first run, before this
commit: enum members became searchable words ("close" finds the `closed` status) and a stop-word list stopped
"in" matching `in-progress` for the doctor task. Six tasks are an illustration, not a
benchmark.

## Is validation right?

Checked against the runtime itself over 1,620 generated filters (every
value of `Aircraft` and `Component`, every operator, ten values of every
kind), run as the maintainer:

- every query it reports no error for, the runtime accepts;
- every query it says can never match returns no row or is refused;
- every condition it says filters nothing returns every row.

The first run of this check found a defect in the validator itself: it
called `ne` with a value the property never has "never matches", when it
matches every row. It is now a warning (`always-matches`).
